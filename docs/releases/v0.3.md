# ADS v0.3 — Release Candidate

**Status: RELEASE TARGET — pending publication.** The release workflow will publish only after validating the exact frozen commit, hosted consumer CI receipts, and the real private Submodule acceptance run. The target commit is not itself a claim that publication has already occurred. Historical acceptance failures remain part of the permanent record. This document is the human-readable release decision, not a claim that all optional host/model combinations passed.

## Stable core scope

ADS v0.3 is a **host-neutral, agent-native development standard**, not a universal native Subagent security product or a hosted benchmark platform.

- **Goal-driven continuous implementation**, proportional planning and scoped authorization. The parent remains responsible for integration, verification and delivery; no mandatory orchestrator, daemon, task database or external review SaaS.
- **Environment discovery and remote-first verification:** reuse existing GitHub Actions / platform previews, autonomously create the smallest authorized task-scoped remote CI or isolated preview where needed, request only truly missing access/approval and keep local testing lightweight. Remote verification never implies permission to increase recurring costs, change IAM, use customer data or alter production.
- **GitHub Project milestone reconciliation** at meaningful checkpoints. Verify actual Issues/PRs/CI/Project fields, do not infer Project state from Markdown.
- **Immutable, review-gated ADS Git Submodule adoption/update**. Pin an exact accessible release SHA; verify local policy/Skill discovery and real consumer CI, and roll back safely when needed. `git submodule update --init` checks out the parent's recorded gitlink; it never implies upgrade to ADS main.
- **Task-aware, optional native Multi-Agent**. Choose serial by default unless a specific host/task has demonstrated safe effective child permissions and a reason for parallel delegation. Delegate only within parent authorization; worktrees do **not** provide a filesystem sandbox. Preserve independent validation, recovery and safe fallbacks.
- **Layered verification and security evidence**. Separate reported/observed model identities, invocation-level permission rules, real OS sandbox behavior, independent application correctness, CI status and production behavior.

## Consumer compatibility and release gates

- [ ] Current ADS candidate main/PR SHA passes the repository's `Validate ADS` workflow, including the 30 existing ADS tests and Markdown/Skill checks.
- [ ] Isolated GitHub-hosted KIRARI and AiringCal trials pass against immutable consumer source SHAs. The trial uses a **local mirror of the ADS checkout within a disposable GitHub Actions runner**, exercises the v0.2 → candidate → rollback submodule/gitlink lifecycle and preserves the original consumer agent instructions; it neither pushes to a consumer nor deploys to production. **This is not evidence that a private nested checkout works across repositories.**
- [ ] The trusted manually dispatched `Skyline-Gazer/ADS-Acceptance-Sandbox` workflow can read and recursively check out private ADS through a narrowly scoped read-only token, verifies gitlink = nested SHA and materializes ADS docs/Skills; the consumer contract job also passes. The publishing workflow validates the run ID and log evidence. Never loosen CI or substitute a mocked checkout to make this check green.
- [ ] The sandbox pin is updated to the **final immutable v0.3 target SHA**, rather than any earlier RC baseline. Hosted CI on that exact sandbox PR head passes and the isolated sandbox upgrade is reviewed/merged.
- [ ] Review the release diff against v0.2 and record known security limitations. No new model benchmark is required just to release the *stable core with opt-in experimental Multi-Agent*.
- [ ] Only after all above conditions pass, create annotated tag `v0.3` at the final validated ADS main commit, publish GitHub Release **ADS v0.3**, verify both resolve to the same commit and that required GitHub Actions checks succeeded. Do not overwrite an existing release/tag.
- [ ] Leave historic failures and unfinished experimental issues visible; close only the explicitly completed acceptance work, with evidence.

## Migration guidance

New consumers should add `.ads` as an immutable Git Submodule at the published `v0.3` commit, keep the root `AGENTS.md` concise and explicitly point to the checked-out ADS policy. Existing adopters should review `v0.2...v0.3` changes, update **only the intended gitlink** in a PR and run their own contracts, CI and preview smoke where applicable. Private GitHub CI consumers require an authorized cross-repository read mechanism (for example, a deploy key with **ADS Contents read-only**); ordinary per-repository `GITHUB_TOKEN` cannot be assumed to read other private repositories. Never embed tokens/private keys in `.gitmodules`, agent instructions, checkout URLs or logs.

No tag, release or production consumer deployment is implied by adding this draft to main. Actual publication and adoption are separate events.
