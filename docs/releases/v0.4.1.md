# ADS v0.4.1 release procedure

**Candidate preparation; publication is not authorized by this document.** Refs [Issue #68](https://github.com/Skyline-Gazer/ADS/issues/68). See [release notes](v0.4.1-notes.md).

The source development PR must merge into dev with a merge commit so the preserved v0.4 publication ancestry remains reachable. Freeze that full dev merge SHA. Independently verify the latest exact-SHA runs for `validate.yml`, `v03-consumer-compat.yml`, `v04-consumer-acceptance.yml`, and `v041-consumer-acceptance.yml`; rerun against dev when necessary. Historical fixed consumer snapshots are compatibility fixtures, not latest adoption evidence.

Use a new same-repository acceptance branch/PR in the existing private ADS-Acceptance-Sandbox. Preserve its canonical `.gitmodules`; verify the candidate gitlink and ordinary Sandbox CI before manually dispatching its trusted main workflow with exact PR number and ADS SHA. Inspect successful run/job logs, credential cleanup and the posted exact-head receipt. Public ADS CI gets no cross-repository secret. Record this independent operator verification explicitly; the ADS repository token cannot query the private receipt itself.

Open an ancestry-preserving release-preparation PR from the frozen dev target to main. Include an Owner-reviewable `release/v0.4.1-publish.json` only after all target receipts exist. Its fields are `version`, `release_approved`, `release_target_sha`, `previous_main_sha`, `source_pull_request`, `notes_sha256`, and `private_consumer_ci`. The receipt binds repository, workflow, successful run ID/URL, consumer PR/head and exact tested ADS SHA, with `verification: operator-verified-successful-run-and-job-logs`. The release notes digest hashes exact UTF-8 file bytes. Before Owner approval keep `release_approved` false; never infer authorization from a green development PR.

After explicit Owner approval, merge the release PR to main with a merge commit. The resulting main tree must differ from the frozen target only by this new publication manifest. The target must contain the previous main as an ancestor; preserve the v0.4 tag, notes, workflows and publication audit commits. No force push, squash/rebase promotion or tag replacement.

The new `release-v041.yml` triggers only a main push changing the v0.4.1 manifest. It runs tests/docs and read-only validation, then revalidates before writes. The publisher refuses drift, inconsistent main ancestry/tree, missing/stale/failed exact-target CI, invalid receipts/notes, lightweight/conflicting tags or conflicting Releases. It creates an annotated immutable tag pointing to the approved target, then a matching Release. A retry resumes after tag-only publication; an exactly matching published Release is a no-op. Re-run the same workflow after transient failure; do not edit an existing tag or Release to force success. Remote main drift requires a fresh reviewed authorization context.

Rollback for consumers is a reviewed Submodule pin back to immutable v0.4, with contract/toolchain/boundary checks as appropriate. A publication rollback preserves the v0.4.1 tag and audit trail and uses a corrective release/PR; it never moves the published tag. This release does not deploy consumer products.
