# Bootstrap a new project

1. Read the user's goal, host/tool restrictions and relevant ADS version. Before feature work, establish the mandatory [Git governance model](../../docs/git-governance.md): `dev` must exist, every task starts from latest `dev`, and changes go through Issue-linked PRs targeting `dev`. If `dev` is missing, establish it through a reviewable bootstrap/migration and verify production/deployment triggers before feature work; never use direct development on `main` as a shortcut. After adding the pinned ADS guidance and governance workflow, copy `templates/git-governance/ensure-ads-branch-protection.py` into the consumer repository as `scripts/ensure-ads-branch-protection.py` through a reviewable change. Inspect actual CI check names and classic protection on `dev` and the production branch; if protection is absent/incomplete, run the helper with one `--required-check` per real blocking check to enable/strengthen and verify it. If admin access or plan support blocks the change, report the exact owner action and do not claim the project is fully compliant.
2. Discover what already exists before choosing a stack or tool: the platform agent's native Skills, `command -v` and version checks for candidate runtimes and package managers, repository scripts, lockfiles and any reachable local service or cache. Record what is **installed**, **configured** and actually **verified**, and keep the scan to a few read-only commands.
3. For the consumer project, run the mandatory CodeGraph + full RTK preflight in [consumer-dev-toolchain.md](../../docs/consumer-dev-toolchain.md). Check latest stable upstream releases, installed versions, initialization and active-host integration separately. Ask before installing missing binaries or changing global host settings. If the binaries already exist but the project is not initialized, initialize them on a development branch; never add the consumer tool manifest/integration to production `main`.
4. Infer runtime, package manager, deployment destination and smallest functional architecture from those findings; ask only if a consequential product or stack decision cannot be safely inferred. Reuse an installed supported runtime and its test facility; if a preferred one is absent, take the smallest documented fallback or report the blocker instead of installing global tooling.
5. Create a runnable minimal vertical slice with appropriate dependency lockfile and common scripts. Add only relevant unit or integration tests and simple CI commands that can really run.
6. By default, add ADS as a pinned Git submodule at `.ads` (or an available project-compatible path), choosing an approved published release or immutable SHA and verifying authorized read access. See [docs/how-to-update.md](../../docs/how-to-update.md) at the repository root. An inaccessible private submodule is a blocker, not installed guidance; do not embed credentials in `.gitmodules`.
7. Render the ADS template `templates/AGENTS.md` at the pinned ADS revision (repository root, not inside this skill directory) using **actual** project paths, commands, auto-deploy effects and sensitive operations. If that file is not locally readable, report the gap instead of inventing a pin. Pin an immutable ADS revision and ensure its text is accessible, not merely a private URL.
8. Add a short architecture/decisions note only for consequential lasting choices. Do not copy unused profiles, empty folders or blanket CI workflows.
9. Validate remotely by default when it materially improves evidence: reuse hosted CI and target-platform preview first. If none exists, create the smallest repo-native hosted workflow or ephemeral preview/test environment autonomously when current authorization, existing credentials, permissions, quotas and budget allow it. Do not incur new recurring spend, upgrade plans, broaden IAM or create long-lived infrastructure without the required grant. If owner action is required, give exact secure setup steps and continue independent safe work; use local fallback only when remote is unnecessary or blocked. Avoid deploying or creating cloud resources outside authorization.

Output: code-ready project and a concise summary. Do not turn bootstrapping into a multi-stage approval workflow.
