# Goal-driven delivery

1. Define observable success and scope. Inspect local project rules and actual merge-to-production implications. Before implementation, follow the mandatory [Git governance policy](../../docs/git-governance.md): use the latest `dev` as the development baseline, track the task with an Issue, work on an isolated task branch, and open a PR targeting `dev`. Never use direct task commits to `dev` or production `main`; production promotion requires a separate release PR.
2. Before a locally running TUI Agent, child or tool starts an access-sensitive task, confirm the enforced canonical project-only read+write boundary under [host-filesystem-boundary.md](../../docs/host-filesystem-boundary.md). Do not read, list, hash, glob, index or explore personal/sibling/outside directories absent explicit scoped Owner approval. Reject permission-mode widening to bypass failures; verify native shell/Read/MCP/child denial with harmless synthetic files and report untested vectors. If the effective host does not restrict reads outside the project, use isolated remote execution or stop sensitive operations.
2. Run one short capability check before implementing: existing runtimes and package managers, the project's declared build/test command, reusable fixtures and already available host Skills or subagents. Reuse those findings for the whole task; repeat only a check of stale assumptions, not a full environment audit.
3. For simple changes implement directly; for large or uncertain work use one concise plan and platform-native workers where helpful.
4. Treat multi-agent as an efficiency choice, not a required number of workers. If the host's native subagents are actually available and bounded independent tasks exist, delegate with a compact contract (goal, dependencies, permitted paths and operations, verification, output). For sensitive data or potentially unauthorized writes, verify effective **per-child** permission limits and real file/shell containment first; some hosts do **not** inherit parent denials, and worktree isolation does **not** block absolute-path writes. Use [docs/native-subagent-safety.md](../../docs/native-subagent-safety.md) for a proportional preflight. Prefer safe read-only parallel exploration or disjoint writes with enforced isolation; otherwise work serially or stop. No child may exceed the parent's explicit authorization or authorize peers.
5. Main agent owns integration: inspect child results/diffs, resolve conflicts, re-run relevant combined tests and distinguish independently observed results from agent claims. If a worker fails, times out or lacks safe isolation, retry narrowly or fall back to serial work without widening scope.
6. Prefer existing architecture and minimum sufficient implementation; reuse existing test facilities, caches and lockfiles before adding frameworks, containers or services. Use necessary mature dependencies; escalate consequential architecture changes.
7. Run relevant tests, examine CI and fix related failures. Use the lowest-cost check that can actually detect the changed behavior, and do not claim offline mocks or reused local fixtures prove live integration. For a deliberate contract/schema break, compare the approved new contract with any target-owned trusted test imports before interpreting a failure: run candidate contract tests only in the existing low-privilege candidate environment and let the trusted gate verify results, never execute candidate-controlled modules with trusted credentials. Follow [contract migration and remote-first guidance](../../docs/execution-and-drift-governance.md#contract-migrations-protect-the-gate-without-freezing-an-obsolete-contract); do not resurrect unsupported legacy parsing solely to satisfy a stale harness.
8. Make a focused Issue-linked PR targeting `dev`; direct task commits to `dev` or production `main` are prohibited. Report checks and risks. Merge autonomously only if low risk, required checks pass and auto-deploy effects are within authorization. Promote production changes only through the separate release/backport PR flow in the Git governance policy.
9. When the current Phase or milestone is actually complete, reconcile linked GitHub Project items and Issues against PR/CI/acceptance before dependent Phase work. Fix only verified drift, close only proved complete work and retain FAIL/PARTIAL blockers; unavailable Project API means PROJECT_UNVERIFIED. See [docs/milestone-reconciliation.md](../../docs/milestone-reconciliation.md). At that boundary, check whether the project's ADS submodule pin has an approved update without auto-upgrading it; use [docs/how-to-update.md](../../docs/how-to-update.md).
10. Distinguish implemented, tested, merged, deployed and live-tested in the summary. Continue working within the current session until goal completion or genuine blocker. Prefer finishing the **existing** task branch/PR: repair in-scope review or CI defects there, verify on the live primary provider, merge when already authorized and eligible, then reread the actual target SHA. Otherwise leave one specific actionable `BLOCKED_WITH_EVIDENCE` report and preserve the PR for resumption. Do not manufacture closure by creating additional approval roles, duplicate Issues, unmerged follow-up PRs, local heavyweight test stacks or unrelated governance branches.

No compulsory per-stage approval, duplicate evidence archive or always-on maintenance scope.

## Remote-heavy execution and lifecycle convergence

Follow [lifecycle and execution governance](../../docs/execution-and-drift-governance.md): choose existing hosted Docker/Compose, browser, performance, SCA and full CI rather than local heavyweight stacks. Local coding, Git and bounded checks remain normal; no silent installation of Docker or browsers. Verify task/PR state before edits; after merge read back target SHA and reconcile Issue/Project/docs before claiming closure. At Phase, release or Provider cutover run full affected drift checks. The receipt checker validates declarations only and does not substitute for live Provider/Project reads.

## Primary provider dispatch

Read [provider selection](../../docs/git-provider.md) and validated .ads-project.json. Submit the Issue-linked PR targeting dev to the configured primary provider. In CNB Primary use current-SHA CNB review and deterministic CI, process feedback and re-review within a capped loop; NPC stays read/comment only unless separately authorized. Do not create a parallel GitHub PR. Production promotion, mirror and tags require separate authority and ref verification.

When CNB Primary is configured use the [CNB review gate and mandatory comment-closure workflow](../../docs/cnb-review.md#mandatory-pr-comment--fix--re-review--agent-merge-closure). Before an Agent-initiated manual PR merge, retrieve **all** PR conversation/inline/CodeBuddy/NPC comments and replies (including any added after the last push), classify and disposition each material finding with comment-specific fix/test evidence or a justified false-positive; explicitly track deferrable low-risk issues. Critical/High and unclosed material Medium findings block. Never infer comment closure from CodeBuddy `passed`, resolved-thread labels or a zero exit code. Re-run review and deterministic CI on the live current head SHA after fixes, recheck merge eligibility just before merging, and verify the resulting dev SHA. Cap automatic fix/re-review cycles at three; stale or missing review and unaddressed blockers mean `BLOCKED_WITH_EVIDENCE`, not a bypass. NPC remains read/comment-only by default. No automatic merge or second human approver is required.

For an approved CNB Primary production release, use [CNB safe synchronization](../../docs/cnb-sync.md) only after the existing reviewable dev-to-main promotion, production-boundary checks and explicit deployment authorization. Dry-run by default, verify both live refs and reject all non-fast-forward or unapproved tags. Do not let PR/NPC jobs access mirror credentials.

## Consumer execution closure

For consumer work (not ADS itself), use the executable [toolchain preflight](../../docs/consumer-dev-toolchain.md#executable-adoption-and-session-preflight-v041) at adoption/session recovery and before graph-dependent work. Bind official version/license/source evidence to the actual executable path and SHA-256. Initialize missing project setup autonomously on the development branch with `--initialize` and an explicit supported host adapter; never install/update global tools without authorization. Validate current-worktree JSON status and a real source-symbol query. Prefer native synchronization; only an observed unhealthy index permits controlled `--recover`. CLI exit 3 requires a separate native-host MCP and RTK interception test, not a VERIFIED claim.

Before production promotion, create a separate clean release-preparation branch while dev retains its integration. Run the generic boundary guard on the exact production tree and actual build output, with the trusted development manifest supplied externally after stripping it. Never treat a source-tree-only check as artifact verification.
