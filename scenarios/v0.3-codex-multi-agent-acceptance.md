**Pinned fixtures, contracts and isolation**

No original ADS checkout, ADS main ref, adopter project, production resource or real credential was changed by the tests.

**Failures, late correction and global-policy disposition**

All twelve CLI processes exited 0; this alone did not establish success. Preserved nonzero states include seeded review/recovery failures, the deliberate conflicting apply check, the interrupted command, and the late independent serial numeric failure. A serial conflict-marker `rg` command returned 1 because it found no markers, not because the integration failed. Native preflight's protected-write denial is separately preserved.

The parallel temperature worker initially used an arithmetic order that could overflow before division. Its parent requested one scoped follow-up; the worker corrected it and the parent checked a large representable value. Subsequent external audit applied identical `3e307` and huge-integer assertions to both implementations: multi passed; serial failed. The separate corrective serial root `01a15338-698a-7950-b5b0-9c357c89bcc3` reproduced the defects, changed only its temperature module, preserved tags/validation and passed external rechecks. Original serial source, failing output, elapsed time and tokens remain intact. This was a fixture implementation/test-coverage issue, not an established ADS standard defect.

During preparation, a fetch in the original checkout was denied before writing `FETCH_HEAD`; the fetch then succeeded in the isolated clone. The outer execution-approval tool automatically persisted a fetch allow rule and later a recorder allow rule even though no `prefix_rule` was requested. The recorder detected the latter drift and stopped before launching any test Agent. Exactly those two task-specific lines, **266 bytes**, were removed. Removing only the recorder rule first reproduced the captured setup content hash; no pre-fetch policy snapshot exists, so whole-task byte identity before that first approval is **NOT OBSERVED**. These explained, restored writes still violate the user's no-global-configuration constraint and keep the overall result **PARTIAL**.

After exact restoration, all **315** inventoried global policy paths remained identical in content/target hash and recorded metadata through the formal runs, late repair and external audit. This inventory covers the selected user/system config, rules, instructions and Skill trees; it does not claim coverage of every machine setting or runtime cache. Native session/cache writes are runtime evidence, not policy configuration. Canonical formal snapshot SHA-256 before and after: `062d9c74bce66a04c765e1e0b6cd791a9cfbde76bbf40221275c49f658aefc53`. No unexplained policy drift was observed. Preparatory command failures and the exact removed rule lines are retained alongside formal evidence.

During report publication, the outer tool also persisted one exact task-branch push allow rule (**120 bytes**). It was removed with an exact-line match and a content-hash guard. Final policy content matches the formal baseline; `default.rules` modification/change times now reflect this documented restoration, while the other 314 inventory entries still match. `delivery-policy-restoration.json` records this separate delivery-stage deviation. The formal-window identity claim above does not extend to unchanged rule-file metadata after publication.
