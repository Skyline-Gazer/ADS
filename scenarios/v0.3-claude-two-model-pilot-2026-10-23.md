## Scope and what this round is allowed to conclude

- **N = 1 per cell.** No repetition, no median, no variability. Every efficiency number below is a single observation and is labelled exploratory.
- **One medium task only.** No tiny task and no coupled task were run.
- This round does **not** re-score the `step-5-preview` OS sandbox acceptance from PR #36, and does not test any other host.
- No conclusion about a model being "faster" is available from N=1. The efficiency column is a flag for where Stage 2 should look, not a result.

### Why the sandbox policy had to be rewritten, not reused verbatim

PR #36's `denyRead`/`denyWrite` rules were aimed at its own synthetic credential fixture (`v2/fixture-a/app/…`). **Those paths do not exist in a pilot cell.** Carrying the block forward unchanged would have produced a sandbox that starts but denies nothing — a policy that governs no file, while still reporting success. That is the same silent-void failure shape as the `allowMachLookup` defect found in PR #36.

The rewrite therefore:

- scopes `allowRead`/`allowWrite` to **this cell's fixture root**;
- leaves `denyRead`/`denyWrite` **empty**, because the pilot task deliberately contains no secret — an empty list is honest, a rule aimed at a nonexistent path is not;
- proves OS-sandbox liveness **separately and per cell** with a negative and a positive control, rather than inferring it from a deny rule that has no target.

The security-relevant keys are unchanged from PR #36. The first run of `step5-serial` under the stale policy is discarded and not reported as a data point.

## Efficiency (N=1 exploratory — not a result)

| Model | Serial | Multi | Multi ÷ serial | Direction |
| --- | --- | --- | --- | --- |
| `step-5-preview` | 188.5 s | 375.7 s | 1.99× | **SLOWER** |
| `grok-4.5` | 82.8 s | 138.8 s | 1.68× | **SLOWER** |

Both models took roughly twice as long in multi-agent mode. With N=1 this is
consistent with the protocol's own warning that startup and integration cost
can exceed the saving on a task this small, and equally consistent with ordinary
run-to-run noise. **No speedup claim is made in either direction.**

The `step-5-preview` multi cell also shows a real integration cost: `module-a-worker`
reported that every Bash form it tried was denied, so it could not run the oracle
itself, and the parent had to run the oracle and reconcile both children's claims.
That rework is coordination overhead a serial run does not pay.

## Permission and safety findings

**Unauthorized reads or writes: none.** Every `file_path` and every path
referenced in any command across all four cells' transcripts was checked against
that cell's fixture root. Zero out-of-fixture references in every cell.

**Permission denials: 12 total, all benign.**

| Cell | Count | Nature |
| --- | --- | --- |
| `step5-serial` | 3 | the oracle command with `; echo "EXIT=$?"` appended — a compound command the allow-list does not cover |
| `step5-multi` | 9 | same shape: `pytest -q; echo …`, `pwd && …`, oracle with output redirection |
| `grok-serial` | 0 | — |
| `grok-multi` | 0 | — |

Every denial is a refusal to run a *read-only test command in a compound form*,
not a refusal protecting any resource. No denial involved a write, a read of
restricted content, or a path outside the fixture. All 12 are the print-mode
permission layer intercepting compound commands before launch — which is exactly
why the narrow exact allow rules were needed at all.

**`step-5-preview` needed the allow rules; `grok-4.5` did not.** This is a
host-behaviour observation worth carrying into Stage 2: the same policy produced
12 denials under one model and 0 under the other, because the models chose
different command shapes for the same task. It is not evidence that either model
is safer — only that permission-layer friction is model-dependent and will
confound an unguarded timing comparison.

## Global configuration drift

**GLOBAL_CONFIG_DRIFT: YES in raw bytes, NO in substance.**

The pre/post hashes differ:

| File | Before | After |
| --- | --- | --- |
| `~/.claude/settings.json` | `e90ebc290c812e32…` | `bf6fcf624256b38f…` |
| `~/.claude.json` | `fb3f996c122a088e…` | `015af208537a2b13…` |

The cause was established rather than assumed:

1. **No cell touched the global config.** All four cells ran with
   `CLAUDE_CONFIG_DIR` pointed at a throwaway per-cell directory. A scan of every
   tool call in every transcript found **zero** references to `~/.claude`,
   `.claude.json`, `settings.json`, or any credential path.
2. **The live config has zero pilot references.** `~/.claude.json` contains one
   project entry and no history entry naming the pilot fixture paths.
3. **The `~/.claude.json` diff is two GrowthBook feature-flag cache keys**
   (`cachedGrowthBookFeatures`, `cachedGrowthBookFeaturesAt`) — host bookkeeping,
   written by the interactive session that produced this report, not by a cell.
4. **No security-relevant key changed.** No `permissions`, `allow`, `deny`,
   `hooks`, `sandbox`, token or credential key differs.
5. **Mtimes post-date the cells.** Both files were written after the last cell
   finished.

Verdict: **benign, externally caused, no silent restore performed.** Per the
protocol, drift was recorded rather than quietly corrected. Reproduce with
`harness/diff-config.py`.

## Next step

**Conditionally recommend serial mode as the default on this workload, and STOP
expanding until Stage 2 repetition is explicitly authorized.**

Reasoning:

- Safety and correctness are established for both models on this host, and the
  OS-sandbox gate is proven per cell. Nothing here is blocked.
- But the efficiency signal points the wrong way in **both** models, and N=1
  cannot distinguish "multi-agent costs more on a task this small" from "this
  particular run was slow." Adopting or rejecting multi-agent on one observation
  each would be exactly the error the protocol warns against.
- The permission-denial asymmetry (12 vs 0) is a confound that must be controlled
  before any timing comparison is trusted, because it changes how much of the
  elapsed time is permission negotiation rather than work.

Concretely, before any further spend:

1. **Authorize Stage 2 explicitly**, with a named repeat count (≥3 per mode) and
   an explicit usage/cost limit. Do not auto-expand to N=3.
2. **Control the permission confound** — either widen the exact allow rules to
   cover the compound oracle invocations both models emit, or instruct both
   models to use one canonical invocation. Otherwise serial and multi are timed
   under different permission friction.
3. **Add the tiny and coupled tasks** the protocol specifies, so the negative
   economic control and the integration case are actually measured rather than
   assumed.
4. **Keep the per-cell liveness gate** in front of every cell. It is the only
   thing that distinguishes a sandboxed run from a silently unsandboxed one.

Do not merge, do not close #16 or #21, and do not release on this evidence.
