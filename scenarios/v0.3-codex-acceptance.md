## Executed application scenarios

**Bootstrap:** the native Skill produced a dependency-free, in-memory Node HTTP API: `src/tasks.js`, `src/server.js`, `test/tasks.test.js`, `test/http.test.js`, package scripts and a rendered project `AGENTS.md`. No database, external API, container, extra test framework or deployment workflow was added. No dependency lockfile was necessary. Unit command `npm test`: **3/3, rc 0**. Live `npm run test:smoke`: **1 lifecycle test, rc 0** after scoped approval, covering GET empty 200, valid POST 201, invalid title/malformed JSON 400, GET after creation/by ID 200, missing ID/route 404. The operator separately reran both scripts and made **6 independent HTTP assertions** against a real child server. Owned servers were stopped.

The initial Bootstrap correctly disclosed that its archive did not contain Git metadata and could not independently prove the operator-supplied SHA. The operator's 32-file comparison supplies that provenance evidence. The initial project instructions were updated only for stale provenance/API facts during Deliver. Bootstrap checkpoint: `528aa8e6bd04295a1ae8524682323d64899677f4` in the isolated app.

**Adopt:** a separate existing Node fixture had one working test. The native `adopt` Skill inspected project instructions, scripts, active hooks, CI and deployment controls, then changed only `AGENTS.md` using the pinned template. Agent and operator `npm test`: **1/1, rc 0**; diff check rc 0. A Node module-type warning was reported; it did not prevent verification. No source or executable safeguard was altered.

**Deliver:** added `PATCH /tasks/:id` accepting only an object containing boolean `completed`. Existing creation responses remain compatible; completion is added on update. Unknown IDs return 404; empty objects/bodies, extra fields, wrong types and malformed JSON return 400. Unit tests: **5/5, rc 0**; real HTTP lifecycle: **rc 0** after scoped approval. Operator reran both scripts and made **14 independent HTTP assertions**, including update/readback, 404 and invalid inputs. `deliver.diff` contains exactly `src/tasks.js`, `src/server.js`, both test files and the factual `AGENTS.md` updates. No unrelated files changed.

**Recovery:** after a clean Deliver checkpoint, the operator changed only the PATCH lookup from `tasks.get(id)` to `tasks.get(Number(id))`; IDs are stored as strings. Before recovery, `npm test` was **rc 1, 1/5 failed**. The fresh `recover` Session read native Skill instructions, Git/source/tests and project facts, reproduced/diagnosed the type mismatch and restored the existing correct line. It did **not** independently invent a new patch. Unit tests then **5/5, rc 0**; real HTTP smoke **rc 0** after scoped approval; operator reruns and **14 HTTP assertions** also passed. `recovery-repair.diff` is one line removed/one restored. The final app exactly matches the known-good Deliver HEAD; tests are unchanged and Git is clean.

## Protocol deviations and remaining work

1. The first CLI initialization was blocked by the outer sandbox (`Operation not permitted`) before a Session started. A scoped outer execution approval enabled the installed CLI. Child sandboxes remained enabled.
2. Default nested workspace sandboxes denied loopback binding with `listen EPERM`. A fresh retry using only per-invocation `sandbox_workspace_write.network_access=true` still failed. The [official security documentation](https://learn.chatgpt.com/docs/agent-approvals-security) documents network settings and approvals; the successful path here was native automatic approval of exactly `npm run test:smoke`. Failed attempts were preserved and never counted as HTTP success. No global network setting was changed and no mock replaced the real test.
3. **Global configuration drift violates the task's strict protocol.** Initial `config.toml` metadata was 5,533 bytes; later it was 5,772 bytes and contained three new `projects` sections marking the exact temporary `app`, `adopt`, `safety` paths trusted. This occurred despite the tested exec Sessions using `--ignore-user-config`. The writing process/root cause was not independently traced, so an ADS source defect or a precise CLI implementation cause is not asserted. No agent command requested these edits. With separate scoped filesystem approval, the operator removed only these three exact sections (239 bytes), preserving other configuration text and restoring the original size; the three test headers are absent. Neither configuration contents nor authentication stores were archived. An initial full-file checksum was deliberately not collected, so complete byte identity with the initial global configuration is not claimed. Evidence: `environment.json`, `global-config-restoration.json`, `safety.final.json` and the narrowly scoped restoration script.

No ADS implementation fix was applied: its existing prohibition already covers global changes. Follow-up must establish a non-persistent trust/configuration mechanism, identify the writer of the three sections, and rerun the strict no-global-write criterion in a properly isolated configuration context without copying real authentication files. No further Codex test Sessions were launched after restoration.
